# GhostShell — Native Chromium 149 Stealth-Patch Audit (2026-06-04)

10-zone specialist audit of the C++ patches in `F:\projects\chromium\src` (Chromium 149.0.7805.0). **95 findings** — critical=13, high=27, medium=29, low=26. 47 new-patch ideas, 40 engine-feature ideas.


## Payload core & plumbing (GhostShellConfig parsing, flag propagation, UA/UA-CH, worker/process coherence, v8 binding integrity)

> The native-C++ design is fundamentally sound and far stealthier than JS injection: spoofs are real getters returning [native code], the --ghost-shell-payload flag propagates to ALL child processes via CopySwitchesFrom in AppendExtraCommandLineSwitches, and the network-service WTF-allocator crash was correctly fixed with a separate std::-based C-bridge store. However the zone has three serious coherence problems: (1) the entire TLS/JA3 cipher_suites & supported_groups vector is dead end-to-end — the .NET builder emits no "tls" key and the GhostShell_GetTLSCipherSuites/SupportedGroups bridge is exported but never called by any consumer, so every profile ships an identical vanilla-Chromium JA3 (only extension-ORDER is per-profile via GetRandomSeed); (2) UA metadata is parsed by THREE independent parsers (GhostBrowserConfig, GhostShellUAOverride, GhostShellConfig) that can diverge — GhostBrowserConfig hardcodes form_factors={"Desktop"} for every profile (wrong for mobile/tablet) and the payload's form_factor key is dropped by all parsers; (3) the claimed Chrome version (143-147) is OLDER than the actual engine (149.0.7805), an engine-vs-UA skew that behavioral feature-detection can catch. Several config getters (GetAcceptLanguage, GetDeviceMemoryRaw, GetTimezoneOffsetMin/Jitter) are dead with no consumer, and the worker V8 isolate never gets a DateTimeConfigurationChangeNotification (relies on env-var/adoptDefault inheritance, which is fragile for early workers).

### `PCP-01` — TLS/JA3 cipher_suites & supported_groups vector is dead end-to-end — all profiles share one vanilla JA3  *(high · coverage-gap)*

- **File:** `F:/projects/chromium/src/third_party/blink/renderer/platform/ghost_shell_config.cc (lines 307-330, 487-512); F:/projects/chromium/src/third_party/boringssl/src/ssl/extensions.cc (4202-4221); F:/projects/ghost_shell_desktop/src/GhostShell.Runtime/Fingerprint/DeviceTemplateBuilder.cs (BuildInternal, no tls key)`
- **Detail:** GhostShellConfig parses tls.cipher_suites/supported_groups into tls_cipher_suites_/tls_supported_groups_ and the C-bridge store populates GhostShellBridge().tls_cipher_suites/groups; GhostShell_GetTLSCipherSuites/GhostShell_GetTLSSupportedGroups are PLATFORM_EXPORTed. But: (a) the .NET DeviceTemplateBuilder.BuildInternal() emits NO "tls" top-level key (grep for cipher_suites/supported_groups/BuildTls returns nothing), so the lists are always empty; (b) a full-tree grep shows GhostShell_GetTLSCipherSuites/SupportedGroups are only DECLARED (weak fwd-decl + weak stub) in extensions.cc and spdy_session.cc and are NEVER CALLED — only ghost_shell_fill_seeds_from_config (which uses GetRandomSeed) is invoked, and it only permutes extension ORDER in ssl_setup_extension_permutation. So the actual cipher-suite list and named-group list in every ClientHello are stock Chromium 149 — identical JA3 across the entire profile fleet, contradicting the header's claim that 'two profiles with different lists produce different JA3s'.
- **Impact:** DataDome/Cloudflare/Akamai JA3/JA3N fingerprinting sees one identical TLS fingerprint for every Ghost Shell profile — a strong cross-profile correlation that links an entire pool to a single tool, and the JA3 won't match the diverse cipher orders real Chrome installs exhibit. Extension-order permutation alone changes JA3 but cipher list is the higher-weight component.
- **Fix:** Wire the producer: add BuildTls() to DeviceTemplateBuilder emitting per-profile-deterministic cipher_suites/supported_groups (derived from the profile seed, drawn from a realistic Chrome 149 cipher set). Wire the consumer: in BoringSSL handshake_client.cc / ssl_client_hello, call GhostShell_GetTLSCipherSuites/SupportedGroups to override the ClientHello cipher list and supported_groups extension when count>0, else keep defaults. Alternatively, if per-profile cipher reordering is too risky, DELETE the dead getters/bridge/store to remove misleading half-wired code.

### `PCP-02` — Three independent UA-metadata parsers can diverge; GhostBrowserConfig wins and hardcodes form_factors={"Desktop"}  *(high · incoherence)*

- **File:** `F:/projects/chromium/src/chrome/browser/chrome_content_browser_client.cc (7513-7619); F:/projects/chromium/src/components/embedder_support/ghost_shell_ua_override.cc; F:/projects/chromium/src/components/embedder_support/user_agent_utils.cc (639-741)`
- **Detail:** ChromeContentBrowserClient::GetUserAgentMetadata() returns GhostBrowserConfig::Get().meta directly (line 7615-7616). GhostBrowserConfig (7566) hardcodes config.meta.form_factors = {"Desktop"} regardless of the payload's mobile/tablet form factor, and never sets form_factors from the payload. Separately, embedder_support::GetUserAgentMetadata() uses a DIFFERENT object (GhostShellUAOverride) which does not parse form_factor at all and keeps native GetFormFactorsClientHint(metadata, metadata.mobile). The two code paths can produce different brand orderings / form factors for the same profile depending on which entry point the network stack hits. Net result for a mobile/tablet profile: mobile=true but Sec-CH-UA-Form-Factors=["Desktop"] — an internal contradiction.
- **Impact:** Sec-CH-UA-Form-Factors / navigator.userAgentData incoherence (mobile bit set but Desktop form factor) is a direct cross-vector lie that CreepJS/FingerprintJS flag. Divergence between subresource Sec-CH-UA headers (one parser) and navigator.userAgentData (another parser) is independently detectable.
- **Fix:** Collapse to ONE source of truth: have ChromeContentBrowserClient::GetUserAgentMetadata() call embedder_support::GetUserAgentMetadata() (which already consults GhostShellUAOverride), and delete the duplicate GhostBrowserConfig parser. Add form_factors parsing to GhostShellUAOverride keyed off the payload (mobile→["Mobile"], tablet→["Tablet"], else ["Desktop"]). Ensure brand-list ordering is identical on both paths.

### `PCP-04` — Claimed Chrome version (143-147) is OLDER than the actual engine (149.0.7805) — engine-vs-UA skew  *(high · currency)*

- **File:** `F:/projects/ghost_shell_desktop/src/GhostShell.Runtime/Fingerprint/ChromeVersions.cs (24-29)`
- **Detail:** The binary is patched Chromium 149.0.7805.0, but ChromeVersions.Versions only contains 143-147 (weighted toward 147.0.7780.88). UA string (BuildUserAgent), Sec-CH-UA brands/full_version_list, and full_version all report <=147 while the real V8/Blink engine is 149. Behavioral feature-detection (new JS/DOM/CSS APIs, header shapes, structuredClone/Intl/Temporal surface, etc. that exist in 149 but not 147) will contradict the claimed version.
- **Impact:** Advanced stacks (CreepJS, custom anti-bot) compare claimed browser version against engine-observable behavior; a 147 UA on a 149 engine is a synthetic-browser tell and also implies the profile claims a version that may already be missing security features it actually has.
- **Fix:** Center the version list on the actual build: either rebuild the engine to match the most-weighted claimed major, or (simpler) update ChromeVersions to include 148/149 weighted toward the true build version, and gate emitted versions so they never exceed the engine's real major. Add a build-time assert that max(emitted major) == engine major.

### `PCP-03` — Payload key form_factor (singular) is dropped — no parser consumes it  *(medium · coverage-gap)*

- **File:** `F:/projects/ghost_shell_desktop/src/GhostShell.Runtime/Fingerprint/DeviceTemplateBuilder.cs (BuildUaMetadata, line ~801 emits "form_factor"); F:/projects/chromium/src/components/embedder_support/ghost_shell_ua_override.cc; chrome_content_browser_client.cc GhostBrowserConfig`
- **Detail:** The .NET BuildUaMetadata emits ua_metadata.form_factor = "desktop"/"mobile"/"tablet" (singular). The native field is form_factors (plural vector). GhostShellUAOverride parses full_version/platform/.../mobile/wow64/brands/full_version_list but NOT form_factor. GhostBrowserConfig parses the same set and hardcodes {"Desktop"}. So the form_factor payload key has no consuming patch (contract MISMATCH).
- **Impact:** The intended form-factor signal never lands; combined with PCP-02 the Sec-CH-UA-Form-Factors header is always Desktop, mismatching mobile UAs.
- **Fix:** Parse ua_metadata.form_factor in the single consolidated UA parser and map it to the form_factors vector using blink::kMobileFormFactor/kTabletFormFactor/kDesktopFormFactor constants.

### `PCP-05` — Worker V8 isolate never receives DateTimeConfigurationChangeNotification(kRedetect) — timezone relies on fragile env/adoptDefault inheritance  *(medium · worker-iframe-leak)*

- **File:** `F:/projects/chromium/src/third_party/blink/renderer/bindings/core/v8/v8_initializer.cc (InitializeMainThread 1054-1085 vs InitializeWorker 1148-1166)`
- **Detail:** The ICU adoptDefault + isolate->DateTimeConfigurationChangeNotification(kRedetect) timezone fix is only in InitializeMainThread(). InitializeWorker() does none of it. Worker correctness currently depends on (a) the browser process setting TZ env var in PreBrowserMain and child processes inheriting it, and (b) ICU adoptDefault being process-global so a later-created worker isolate's createDefault() picks it up. This holds for workers created after main-thread init, but the worker isolate's own V8 Date cache is not explicitly invalidated, and there is a window/edge case (very early workers, service-worker startup before a document) where the cached zone could be stale.
- **Impact:** If a worker's Intl.DateTimeFormat().resolvedOptions().timeZone or Date().getTimezoneOffset() ever diverges from the main frame, that is a classic heavily-weighted detection (value differs in Worker vs main frame).
- **Fix:** In V8Initializer::InitializeWorker(), after InitializeV8Common, replicate the GhostShellConfig timezone block: re-adopt the ICU default from GetTimezoneId() (idempotent/cheap) and call isolate->DateTimeConfigurationChangeNotification(kRedetect) so every worker isolate's Date cache is explicitly synced.

### `PCP-06` — GetAcceptLanguage() config getter is dead; Accept-Language HTTP header not pinned to payload  *(medium · coverage-gap)*

- **File:** `F:/projects/chromium/src/third_party/blink/renderer/platform/ghost_shell_config.h (50); ghost_shell_config.cc (135-136 parses accept_language); F:/projects/ghost_shell_desktop/src/.../ChromeOptionsBuilder.cs (89 --lang)`

So the q-weighted Accept-Language string in the payload is ignored and the header is Chromium's default expansion of --lang, which may not exactly equal the payload's accept_language or the navigator.languages list shape.
- **Impact:** Potential mismatch between the Accept-Language request header and navigator.languages (order/q-values) — a coherence signal some stacks check. Also a contract MISMATCH (payload field + getter with no consumer).
- **Fix:** Either consume GetAcceptLanguage() to override the Accept-Language header at the network layer (RendererPreferences.accept_languages / URLLoader) so it exactly matches the payload, or remove the dead getter/field and document that --lang is the single source. Ensure navigator.languages and Accept-Language are derived from the same ordered list.

### `PCP-10` — --no-sandbox is always passed — a hard headless/automation tell  *(medium · detection-leak)*

### `PCP-07` — GetDeviceMemoryRaw() is dead and unrealizable — performance.memory.jsHeapSizeLimit not spoofed  *(low · incoherence)*

- **File:** `F:/projects/chromium/src/third_party/blink/renderer/platform/ghost_shell_config.h (40-41); F:/projects/ghost_shell_desktop/src/.../DeviceTemplateBuilder.cs (ClampMemory 270-279)`
- **Detail:** GetDeviceMemoryRaw() is documented for performance.memory.jsHeapSizeLimit coherence and is supposed to carry values >8 (e.g. 16). But (a) no patch consumes GetDeviceMemoryRaw() (only the header matches), and (b) .NET ClampMemory caps device_memory at 8 before emission, so the raw value can never exceed 8 anyway. performance.memory.jsHeapSizeLimit therefore reflects the real V8 heap limit, not the spoofed device.
- **Impact:** Minor cross-vector incoherence (deviceMemory bucketed vs real jsHeapSizeLimit). Low severity because real Chrome's jsHeapSizeLimit is a fixed ~2-4GB independent of RAM, so the leak is subtle, but the dead getter + misleading comment invite future bugs.
- **Fix:** Either implement a performance.memory patch that consumes GetDeviceMemoryRaw() (and have .NET emit an unclamped raw value separately from the W3C-bucketed device_memory), pinning jsHeapSizeLimit to a realistic per-profile value, or delete GetDeviceMemoryRaw() and the misleading comment.

### `PCP-08` — String config fields overwrite their defaults with null when a sub-key is missing (forward-compat hazard)  *(low · correctness)*

- **File:** `F:/projects/chromium/src/third_party/blink/renderer/platform/ghost_shell_config.cc (127-128, 158, 164-168, 187, 205-209, 252-258)`
- **Detail:** All String fields are assigned via field_ = ToBlinkString(dict->FindString(key)), which returns a null String when the key is absent, unconditionally overwriting the header default (e.g. connection_effective_type_="4g", connection_type_="wifi", platform_="Win32", timezone_id_="Europe/Kyiv"). Ints/doubles correctly use value_or(default). If a section dict is present but omits a string key (e.g. an older payload after a field is added), the default is silently wiped to null. Current .NET always emits all keys so it is latent, but it breaks the documented forward-compat guarantee in the noise-seed comment block.
- **Impact:** A future/older payload could blank navigator.platform, connection type, timezone id, etc., causing 'undefined-shaped' values that are themselves tells, or falling through to native (real) values in an inconsistent way.
- **Fix:** Use a guarded helper: only assign when FindString returns non-null, e.g. if (const std::string* s = dict->FindString(key)) field_ = ToBlinkString(*s); preserving the default otherwise — mirroring the value_or pattern already used for numerics and the gpu block (276-281).

### `PCP-09` — GetTimezoneOffsetMin()/GetTimezoneOffsetJitter() are dead getters (documented ±1min drift never implemented)  *(low · coverage-gap)*

- **File:** `F:/projects/chromium/src/third_party/blink/renderer/platform/ghost_shell_config.h (99,148, comment 134)`
- **Detail:** GetTimezoneOffsetMin and GetTimezoneOffsetJitter have no consumer (grep matches only the header). The header comment 'tz_* → Date::getTimezoneOffset (±1 minute drift)' is unimplemented. Date.getTimezoneOffset() is instead correctly derived from the ICU default zone set via adoptDefault, so the offset is coherent — but the getters and the jitter design are dead.

- **Fix:** Remove GetTimezoneOffsetMin/GetTimezoneOffsetJitter and the timezone_offset_* fields plus the misleading comment, OR if a self-check reads them, keep GetTimezoneOffsetMin but compute it from the actual ICU zone so it cannot drift from getTimezoneOffset(). Do NOT add ±1min jitter — it would reduce realism.

### `PCP-11` — Brand list is emitted in fixed canonical order; verify it matches the real 149 engine's GREASE permutation  *(low · detection-leak)*

- **File:** `F:/projects/ghost_shell_desktop/src/GhostShell.Runtime/Fingerprint/DeviceTemplateBuilder.cs (BuildUaMetadata 772-789); F:/projects/chromium/src/components/embedder_support/user_agent_utils.cc (ShuffleBrandList 266-287, GetRandomOrder)`
- **Detail:** The .NET emits brands/full_version_list in a fixed order (Not_A Brand, Chromium, Google Chrome) with GREASE brand 'Not_A Brand' v8. Real Chrome derives the brand order AND the GREASE token via a seed (ShuffleBrandList/GetGreasedUserAgentBrandVersion) that is deterministic per major version. If that fixed order/GREASE token does not equal what stock Chrome 149 would produce for its major version, navigator.userAgentData.brands ordering is a mismatch; and identical ordering across all profiles is at least a weak correlation if real users vary by version.
- **Impact:** Mismatched or atypical Sec-CH-UA brand ordering / GREASE token vs what the claimed Chrome version really emits is a CreepJS-class UA-CH consistency signal.
- **Fix:** Generate the brand list (order + GREASE brand/version) using the SAME seed-driven algorithm Chromium uses for the claimed major version, so navigator.userAgentData.brands is byte-identical to a real Chrome of that version. Tie this to PCP-04 (correct claimed version) and PCP-02 (single parser).

**Engine-feature ideas:**

- **Build the stealth driver into the engine (drop ChromeDriver/CDP automation surface)** — The whole stack is driven by Selenium/ChromeDriver with CDP (Network.enable, DOMStorage.enable, ExecuteScript), which is a large, well-known detection surface (Runtime.enable console hook, CDP timing, DevToolsActivePort). A native in-engine automation channel (mojo IPC from the .NET host, no DevTools protocol, no ChromeDriver) would remove the single biggest residual bot tell that the otherwise-excellent native spoofing cannot hide.
- **Compile-time payload binding (no plaintext --ghost-shell-payload on the command line)** — The base64 payload sits on the chrome.exe command line, readable by any local process via the process list and reconstructable from crash dumps; it also makes every flag (including --no-sandbox, --disable-blink-features=AutomationControlled) enumerable. Deliver the payload over an inherited pipe/shared-memory handle or an encrypted file descriptor resolved in PreSandboxStartup, so neither the spoof config nor the automation flags are visible in the process command line.
- **Centralize all GhostShell config behind one PLATFORM_EXPORT singleton + generated getters** — There are currently at least 4 separate command-line re-parsers (GhostShellConfig, GhostShellUAOverride, GhostBrowserConfig, GhostTzConfig, plus the C-bridge store), each independently base64-decoding and JSON-parsing the payload. Consolidating to one parse with typed cross-process accessors removes the divergence class of bugs (PCP-02), the dead-getter class (PCP-01/06/07/09), and reduces startup cost; a codegen step from the .NET schema would keep producer and consumer keys in lockstep and statically flag any dropped/orphan key.
- **Native sandbox-compatible stealth so --no-sandbox can be removed** — Patching the specific subsystems that currently force --no-sandbox (so the renderer/GPU sandbox stays on) eliminates a fleet-wide automation correlate (PCP-10) and improves real security. This is an engine-level fix: identify which stealth patch breaks under sandbox isolation (likely a syscall or shared-memory access added by a spoof) and route it through a brokered, sandbox-safe path.


## navigator.* identity (UA / platform / languages / hardwareConcurrency / deviceMemory / vendor / webdriver)

> The core navigator identity surface is mostly well-wired and native (no JS shims, so Function.prototype.toString integrity is intact for every getter), and the patches correctly ride NavigatorBase so userAgent/hardwareConcurrency/languages propagate into dedicated/shared/service workers via the propagated --ghost-shell-payload switch. webdriver is hardcoded false. However there is one CRITICAL cross-context leak: navigator.platform is read from NavigatorBase::platform(), which was NOT patched and returns the build-time platform (GetReducedNavigatorPlatform), so the GhostShell hook in navigator_id.cc::platform() is shadowed and dead on desktop and in workers — a profile spoofing macOS/Linux on a Windows build leaks "Win32". Two vectors are half-wired: the Accept-Language HTTP header is never sourced from config (it comes from profile prefs/app locale), so navigator.languages can diverge from the Accept-Language header; and the entire Blink-side UA-metadata getter family plus GetLanguage/GetAcceptLanguage are parsed but have no consumer (the real CH spoof lives in a parallel embedder/browser path), creating a triple-parse maintenance hazard where the three copies can drift. There is also a debug VLOG + an unconditional native-memory probe left in the deviceMemory hot path.

### `NAV-001` — navigator.platform GhostShell patch is shadowed/dead on desktop and in workers  *(critical · incoherence)*

- **File:** `F:/projects/chromium/src/third_party/blink/renderer/core/execution_context/navigator_base.cc`
- **Detail:** NavigatorBase inherits NavigatorID (navigator_base.h:43) and OVERRIDES platform() (navigator_base.h:54, navigator_base.cc:59-68). NavigatorBase::platform() returns GetReducedNavigatorPlatform() (a hardcoded build-flag value: 'Win32'/'MacIntel'/'Linux x86_64') and only ever calls NavigatorID::platform() on Android when the reduce flag is off. The GhostShell hook lives in NavigatorID::platform() (navigator_id.cc:61-66), which is therefore never reached on desktop. Main-frame Navigator::platform() (navigator.cc:58-68) calls NavigatorBase::platform() (the unpatched override), and WorkerNavigator has no platform() override so it also resolves to NavigatorBase::platform(). Net: navigator.platform == build-time OS, NOT config platform, in BOTH main frame and workers. On a Windows build this silently coincides with the common 'Win32' default, masking the bug.
- **Impact:** Any profile spoofing a non-build OS (e.g. macOS 'MacIntel' or 'Linux x86_64' on a Windows host build) leaks navigator.platform='Win32' while navigator.userAgent, Sec-CH-UA-Platform and userAgentData.platform all say Mac/Linux. CreepJS, FingerprintJS, Iphey and Pixelscan all cross-check navigator.platform against the UA platform token and Sec-CH-UA-Platform; a mismatch is a hard, heavily-weighted lie-detector hit. Even same-OS, navigator.platform in a Worker is compared against the main frame and against the UA — any drift is flagged.
- **Fix:** Move the GhostShell override into NavigatorBase::platform() (so it covers both Navigator and WorkerNavigator): at the top of NavigatorBase::platform(), `if (GhostShellConfig::GetInstance().IsActive()) { String p = GhostShellConfig::GetInstance().GetPlatform(); if (!p.empty()) return p; }` before the GetReducedNavigatorPlatform() return. Keep the navigator_id.cc hook for the Android NavigatorID path. Verify navigator.platform equals config in a Worker and matches the UA platform token + Sec-CH-UA-Platform for a cross-OS profile.

### `NAV-002` — Accept-Language HTTP header not sourced from config — diverges from navigator.languages  *(high · incoherence)*

- **File:** `F:/projects/chromium/src/chrome/browser/chrome_content_browser_client.cc`

### `NAV-003` — Debug VLOG and unconditional native deviceMemory probe left in hot getter  *(medium · performance)*

- **File:** `F:/projects/chromium/src/third_party/blink/renderer/core/frame/navigator_device_memory.cc`
- **Detail:** NavigatorDeviceMemory::deviceMemory() (lines 18-44) keeps a process-static `int call_count` plus VLOG(1) diagnostics for the first 5 calls, and on EVERY call unconditionally computes `float native = ApproximatedDeviceMemory::GetApproximatedDeviceMemory();` even when the spoof is active and will be returned. ## Canvas 2D & image (canvas-hash noise + text metrics)

> This zone is functionally wired but internally incoherent and leaky. Canvas pixel noise is implemented in TWO independent code paths with TWO completely different algorithms and magnitudes: getImageData() uses a per-call LCG that perturbs EVERY RGB channel of EVERY pixel by up to +/-1.5*noise_amp*255 (read in base_rendering_context_2d.cc lines 541-576), while the toDataURL/toBlob/convertToBlob encode path uses a SplitMix64 +/-1 LSB hash gated to ~1-in-N pixels keyed on (seed,x,y) (image_data_buffer.cc lines 71-109). These produce mutually inconsistent, statistically distinguishable noise for the same canvas, and the getImageData amplitude is large enough to be a visible/anomalous noise floor. Worse, the primary main-thread toBlob() PNG/JPEG path encodes rows directly off raw src_data_ and never calls the noise function at all, so toBlob is un-noised while toDataURL is noised. measureText() adds a per-profile width offset that is NOT applied to actual text rendering, so measureText().width disagrees with the rendered glyph advances. canvas_shift is parsed and exposed but consumed nowhere. Worker/OffscreenCanvas propagation is OK (process-global singleton + shared BaseRenderingContext2D), but the encode-path gap and algorithm divergence are critical detection signals.

### `CANVAS-01` — Two divergent canvas-noise algorithms produce inconsistent fingerprints across readback paths  *(critical · incoherence)*

- **File:** `F:/projects/chromium/src/third_party/blink/renderer/modules/canvas/canvas2d/base_rendering_context_2d.cc (lines 541-576) and F:/projects/chromium/src/third_party/blink/renderer/platform/graphics/image_data_buffer.cc (lines 58-109)`
- **Detail:** getImageData() noise: an LCG (rng = rng*1103515245+12345) reseeded from GetRandomSeed()^0xA5A5A5A5, applied to EVERY R,G,B of EVERY pixel, delta in range +/-(noise_amp*1.5*255). ImageDataBuffer noise (toDataURL/toBlob/convertToBlob): SplitMix64 keyed on seed^x^(y<<32), gated to 1-in-N pixels (N=1/canvas_noise), only +/-1 LSB. The two paths read the SAME canvas but emit completely different noise distributions, magnitudes, and spatial patterns. A detector that renders identical content and compares getImageData() pixels against the decoded toDataURL() pixels sees a contradiction no real GPU/driver exhibits (real readback noise is identical regardless of which API extracts it).
- **Impact:** CreepJS/FingerprintJS cross-check the canvas hash via multiple extraction APIs. Differing per-API noise (and the getImageData amplitude being orders of magnitude larger than the toDataURL LSB noise) is a strong 'lie detector' signal: the pixels are being tampered with, and inconsistently.
- **Fix:** Unify on ONE noise function in a shared helper (e.g. GhostShellApplyCanvasNoise in a common header) keyed strictly on (seed, x, y) with a fixed small amplitude (+/-1 LSB, low density). Call it from getImageData() operating on image_data->RawByteSpan() with the SAME (x=sx+col, y=sy+row) global coordinates so a sub-rect read matches the full read, and from ImageDataBuffer for encode paths. Remove the per-call LCG entirely.

### `CANVAS-02` — Main-thread toBlob() PNG/JPEG bypasses canvas noise entirely (progressive encodeRows path)  *(critical · detection-leak)*

- **File:** `F:/projects/chromium/src/third_party/blink/renderer/core/html/canvas/canvas_async_blob_creator.cc (InitializeEncoder lines 510-535, IdleEncodeRows lines 373-410, ForceEncodeRows 412-429)`
- **Detail:** For HTMLCanvasElement.toBlob() with PNG/JPEG on the main thread, use_idle_encoding is true, so the encoder is created via ImageEncoder::Create(&encoded_image_, src_data_, ...) and driven row-by-row with encoder_->encodeRows(1) directly over the RAW src_data_ SkPixmap. This path NEVER calls ImageDataBuffer::EncodeImage / GhostShellApplyCanvasNoise. Only the non-idle fallbacks (worker convertToBlob, webp, off-thread EncodeImageOnEncoderThread) go through EncodeImage. So toBlob (the common case) is un-noised while toDataURL (image_data_buffer.cc ToDataURL) IS noised.
- **Impact:** An anti-bot script can hash canvas.toBlob() output and compare it to canvas.toDataURL() output of the same canvas. toDataURL carries +/-1 LSB noise, toBlob does not -> the two disagree, and toBlob matches an un-spoofed Chromium baseline (de-anonymizing the real GPU rasterization). DataDome/Cloudflare commonly use toBlob.
- **Fix:** Apply the unified noise to src_data_ ONCE at CanvasAsyncBlobCreator construction (or in ScheduleAsyncBlobCreation before InitializeEncoder), so every downstream path (idle encodeRows, ForceEncodeRows, off-thread, in-thread EncodeImage) sees already-noised pixels. Do not rely on ImageDataBuffer::EncodeImage which is skipped by the progressive path.

### `CANVAS-03` — getImageData noise amplitude is far too large and applied to 100% of pixels  *(high · correctness)*

- **File:** `F:/projects/chromium/src/third_party/blink/renderer/modules/canvas/canvas2d/base_rendering_context_2d.cc (lines 558-571)`
- **Detail:** delta = (rand/255)*noise_amp*255*3 - noise_amp*255*1.5 gives a uniform jitter of +/-(noise_amp*1.5*255) on EVERY channel of EVERY pixel. With a typical noise_amp around 0.001-0.003 that is +/-0.4 to +/-1.1, but the config comment for canvas_noise describes it as a DENSITY (0..0.003 meaning ~3 pixels per thousand), not an amplitude. base_rendering_context_2d.cc misinterprets the same field as an amplitude multiplier. If a profile sets canvas_noise to e.g. 0.01 (still plausibly 'small'), getImageData jitter becomes +/-38 per channel - grossly visible and statistically impossible for real readback.
- **Impact:** High per-pixel variance across the whole image is a textbook canvas-poisoning signature: the noise histogram is uniform across all pixels rather than the sparse, structured driver dither real hardware shows. CreepJS flags broadband canvas perturbation.
- **Fix:** Reinterpret canvas_noise consistently as density everywhere (matching image_data_buffer.cc), gate to 1-in-N pixels, and cap amplitude at +/-1 LSB. Share the helper per CANVAS-01 so this divergence cannot recur.

### `CANVAS-04` — measureText() width offset is not applied to rendered text, breaking metrics/render coherence  *(high · incoherence)*

- **File:** `F:/projects/chromium/src/third_party/blink/renderer/core/html/canvas/text_metrics.cc (lines 120-150) vs F:/projects/chromium/src/third_party/blink/renderer/modules/canvas/canvas2d/base_rendering_context_2d.cc DrawTextInternal (lines 1042-1191)`

- **Fix:** Either (a) drop the measureText width offset and rely solely on the FontCache allowlist + pixel noise for text-fingerprint variance, or (b) apply the identical per-string offset to the rendering advance in DrawTextInternal (add it to font_width before alignment/scaling) AND shift actualBoundingBox/glyph_bounds by the same delta so all TextMetrics fields stay coherent.

### `CANVAS-06` — getImageData noise ignores the read sub-rectangle origin (sx,sy), so partial vs full reads disagree  *(high · detection-leak)*

- **File:** `F:/projects/chromium/src/third_party/blink/renderer/modules/canvas/canvas2d/base_rendering_context_2d.cc (lines 550-571)`
- **Detail:** The LCG walks the returned buffer linearly from index 0 regardless of sx/sy. So getImageData(0,0,W,H) and getImageData(10,10,W-10,H-10) apply DIFFERENT noise to the same underlying canvas pixel (the pixel at (10,10) gets the rng state for buffer-index 0 in the second call but for index (10*W+10)*... in the first). - **Impact:** Sub-rect vs full-rect read inconsistency is a direct tamper tell. It also means measureText/text pixel sampling at known offsets is non-deterministic relative to a full read.
- **Fix:** Key the noise on absolute canvas coordinates: for each output pixel at buffer row r, col c, compute global (x=sx+c, y=sy+r) and feed (seed,x,y) into the shared SplitMix gate. This makes any sub-rect a consistent slice of the full-image noise field and matches the encode path exactly.

### `CANVAS-05` — canvas_shift config field is parsed and exposed but consumed by no patch (dead vector)  *(medium · coverage-gap)*

### `CANVAS-07` — createImageBitmap / captureStream / transferToImageBitmap readback paths are not noised  *(medium · missing-vector)*

### `CANVAS-08` — getImageData noise runs even on accelerated zero-initialized / out-of-bounds buffers, perturbing transparent padding  *(low · correctness)*

## WebGL & WebGPU

> The WebGL vector is broadly wired (UNMASKED vendor/renderer override covers WebGL1 and WebGL2 via fall-through, extension allowlist + always-keep core, getParameter/shader-precision/aliased-range jitter) and the process-wide config singleton means OffscreenCanvas-in-worker inherits the same spoof. ### `WG-03` — readPixels (and the entire rendered-pixel WebGL hash) carries NO noise despite config header claiming it does  *(critical · missing-vector)*

### `WG-05` — getShaderPrecisionFormat +/-1 jitter produces precision/range values inconsistent with the claimed renderer  *(medium · detection-leak)*

### `WG-06` — webgl_params_mask bits are overloaded across unrelated parameters (single bit toggles multiple params)  *(medium · correctness)*

- **File:** `webgl_rendering_context_base.cc (GetIntParameter 8017-8039 uses bits 3-12; GetWebGLFloatArrayParameter 8070-8082 uses bits 3 & 4; GetWebGLIntArrayParameter 8108-8117 uses bit 5) + DeviceTemplateBuilder.cs (webgl_params_mask = rng[0x3,0x40), line 646)`

## Web Audio (AudioContext sampleRate/latency, AudioBuffer noise, AnalyserNode frequency/time-domain data)

> The Web Audio zone is only half-wired and the noise that exists is detectable. sampleRate() spoofing (base + seed jitter, realtime-only) is correct and coherent, but the AudioBuffer/Analyser noise is fundamentally weak: getChannelData() adds a *constant DC offset to only the first ≤100 samples once per buffer, while copyFromChannel() (the dominant FingerprintJS/CreepJS read path) bypasses noise entirely, so the standard OfflineAudioContext+compressor audio fingerprint is either unnoised or noised in a region the fingerprinter never reads. getFloatFrequencyData/getByteFrequencyData add a uniform additive dB constant (shape-preserving = defeated by normalization), and getFloatTimeDomainData/getByteTimeDomainData get NO noise at all. Three config fields (GetAudioBaseLatency, GetAudioOutputLatency, GetAudioMaxChannelCount) are completely dead — baseLatency/outputLatency/maxChannelCount still return real hardware values, and baseLatency is derived from the spoofed sampleRate producing incoherent latency numbers.

### `WA-01` — copyFromChannel() bypasses audio noise entirely — the dominant FP read path is unnoised  *(critical · detection-leak)*

- **File:** `F:/projects/chromium/src/third_party/blink/renderer/modules/webaudio/audio_buffer.cc`
- **Detail:** The only AudioBuffer noise injection lives in getChannelData() (lines 216-239). copyFromChannel() (lines 247-284) reads channels_[channel_number]->AsSpan() directly into the destination and never calls getChannelData() nor applies GetAudioOffset(). FingerprintJS / CreepJS audio fingerprinting renders an OscillatorNode through a DynamicsCompressorNode in an OfflineAudioContext and reads the result; many implementations use copyFromChannel (or read steady-state samples), which returns the pristine, un-noised PCM. So the canonical audio fingerprint hash is byte-identical to vanilla Chromium for any profile that uses the copyFromChannel path.
- **Impact:** An anti-bot stack computes the audio hash via OfflineAudioContext+copyFromChannel and gets the SAME hash across all Ghost Shell profiles (collision → pool detection) AND a hash matching unpatched Chromium 149 (template detection). Either is a hard fail on CreepJS/FingerprintJS audio entropy.
- **Fix:** Route copyFromChannel through the noised accessor: replace `channels_[channel_number].Get()->AsSpan()` with a call to getChannelData(channel_number) so the same per-sample noise is applied, OR (better) move noise out of getChannelData into a single private EnsureNoised(channel) helper invoked by getChannelData, copyFromChannel, and CreateSharedAudioBuffer so every read path is covered identically.

### `WA-02` — Audio noise is a constant DC offset on only the first 100 samples — not hardware-like and trivially detectable  *(critical · detection-leak)*

- **File:** `F:/projects/chromium/src/third_party/blink/renderer/modules/webaudio/audio_buffer.cc`
- **Detail:** getChannelData() (lines 224-235) does `data[i] += offset` for i in [0, min(len,100)) with a single scalar offset from GetAudioOffset(). This (a) only touches the first 100 of typically 44100+ rendered samples, (b) adds an identical constant to every one of those samples (a DC step, not noise), and (c) latches via noise_applied_ so it runs once. Real audio-stack entropy is a diffuse sub-LSB perturbation spread across the whole signal. The standard audio FP reads steady-state samples (~index 4400-5000 after the compressor settles), which are entirely outside the first 100 — so the fingerprinted region is untouched even via getChannelData.
- **Impact:** Two failures at once: the fingerprinted sample window is unmodified (hash = vanilla → template/pool collision), and if a detector DOES inspect samples 0-99 it sees an unnatural constant additive step (DC bias on a windowed oscillator) that no real audio pipeline produces — a positive 'tampered' signal.
- **Fix:** Apply seed-driven per-sample noise across the ENTIRE channel, magnitude ~1e-7 to 1e-5 (sub-perceptual, FP-relevant). Use a deterministic PRNG seeded from GetRandomSeed()+channel_index so it is stable per profile / unique across, e.g. for each i: data[i] += (hash(seed, i) normalized to [-1,1]) * audio_offset_scale. Do NOT use a constant offset and do NOT cap at 100 samples.

### `WA-03` — getFloatTimeDomainData / getByteTimeDomainData have no noise  *(high · coverage-gap)*

- **File:** `F:/projects/chromium/src/third_party/blink/renderer/modules/webaudio/realtime_analyser.cc`
- **Detail:** GetFloatFrequencyData (lines 119-124) and GetByteFrequencyData (lines 153-156) add audio_off; but GetFloatTimeDomainData (lines 170-194) and GetByteTimeDomainData (lines 196-224) copy input_buffer_ to the destination verbatim with no GhostShell hook. - **Impact:** A fingerprinter using AnalyserNode.getFloatTimeDomainData/getByteTimeDomainData (a known alternative to the OfflineAudioContext path) sees the real waveform — no per-profile entropy, identical across profiles and to vanilla Chromium.

### `WA-04` — Frequency-data noise is a uniform additive dB constant — defeated by normalization  *(high · detection-leak)*

- **File:** `F:/projects/chromium/src/third_party/blink/renderer/modules/webaudio/realtime_analyser.cc`
- **Detail:** Both GetFloatFrequencyData (line 122: db_mag = LinearToDecibels(linear_value) + audio_off) and GetByteFrequencyData (line 156) add the SAME scalar audio_off to every bin. A constant offset across all bins preserves the spectral shape and every inter-bin delta; any fingerprinter that normalizes (subtracts mean / uses bin-to-bin differences / hashes shape) gets an identical result to vanilla. For GetByteFrequencyData the constant is additionally swallowed by the min/max dB clamp-and-quantize, so for typical default min/max (-100/-30 dB) a ~2.7e-4 dB offset rounds away to zero in the uint8 output entirely.
- **Impact:** CreepJS-style normalized audio hashing is unaffected (no per-profile entropy in shape). The byte path noise is effectively a no-op after quantization — zero entropy contribution.

Ensure the byte path perturbation is large enough to survive the UCHAR_MAX*(db-min)/(max-min) quantization (perturb before scaling and size it relative to the dB window).

### `TIMING-01` — performance.now() jitter breaks monotonicity and re-adds sub-clamp resolution  *(critical · detection-leak)*

- **File:** `F:/projects/chromium/src/third_party/blink/renderer/core/timing/performance.cc:1273-1284`
- **Detail:** Performance::now() returns MonotonicTimeToDOMHighResTimeStamp(...) which is already coarsened by TimeClamper to 100µs (coarse) / 5µs (fine) discrete steps. The GhostShell patch then does `t += base::RandDouble() * 0.1 - 0.05;` adding ±0.05ms (±50µs) of continuous, NON-deterministic float noise on top. Two consequences: (a) MONOTONICITY VIOLATION — consecutive now() calls can return a smaller value than the previous one (real Chrome's performance.now() is monotonically non-decreasing; the clamper preserves this, the +RandDouble destroys it). (b) RESOLUTION LEAK — the returned values are no longer integer multiples of the 100µs clamp step; `now() % 0.1` becomes a continuous uniform distribution instead of the discrete spike pattern a clamped clock produces. base::RandDouble is also not seed-driven, contradicting the per-profile stability doctrine.
- **Impact:** CreepJS, FingerprintJS and custom DataDome/Akamai timing probes do exactly this: tight-loop now() and (i) flag any t[i+1] < t[i] decrease (impossible on real Chrome, common here) and (ii) histogram now()%resolution to recover the clock granularity. A continuous distribution + non-monotonic samples is a strong, heavily-weighted automation signal — worse than leaving the clock unpatched, because vanilla Chrome's clamp is already private and bot-neutral.
- **Fix:** Remove the +RandDouble entirely (Chromium's TimeClamper already provides per-process-secret randomized-threshold coarsening that is private AND monotonic AND indistinguishable from stock Chrome). If per-profile variation is truly wanted, do NOT add post-clamp float noise; instead seed TimeClamper::secret_ from GhostShellConfig::GetRandomSeed() (time_clamper.cc:18) so the randomized rounding threshold is profile-stable while remaining monotonic and snapped to the legal resolution grid. Apply the same to any other now()-like surfaces (event timeStamp, PerformanceEntry.startTime) for consistency.

## Fonts

> The Fonts zone is only half-wired. The per-profile allowlist (GhostShellConfig::GetFontList) is enforced in exactly two places: FontCache::GetFontData (the CSS font-family render path) and FontAccess::queryLocalFonts. ## TLS / JA3 (ClientHello cipher suites, supported groups, extension ordering — JA3/JA4)

> The TLS zone is the single weakest stealth vector in Ghost Shell: it is structurally half-wired and silently inert in production. The full C++/BoringSSL chain (config.cc parser, WTF-free C bridge, ssl_client_socket_impl.cc cipher/group override, extensions.cc per-profile extension permutation) is competently written, but the .NET DeviceTemplateBuilder.Build() NEVER emits a "tls" key (confirmed at DeviceTemplateBuilder.cs lines 164-182 and by CoherenceValidator.cs line 271 "field not present in fingerprint"). Therefore GhostShell_GetTLSCipherSuites and GhostShell_GetTLSSupportedGroups always return 0, the cipher and supported_groups overrides never fire, and every profile ships an identical Chrome-default cipher list, identical supported_groups, and identical signature_algorithms. The ONLY per-profile TLS variation is ClientHello extension ORDER (seeded from noise.seed, which IS emitted) — which classic JA3 sees but JA4/JA4_r deliberately sort away, so JA4 is constant across the entire profile pool. Additionally, even if "tls" were emitted, the override cannot change the TLS 1.3 cipher suites (the suites JA4 actually fingerprints on a 1.3 handshake) because those are written from hardcoded BoringSSL arrays, and the key_share extension is not kept coherent with an overridden group list in a Chrome-faithful way.

### `TLS-01` — Payload never emits a "tls" key — entire cipher/group override is dead in production  *(critical · coherence)*

- **File:** `F:/projects/ghost_shell_desktop/src/GhostShell.Runtime/Fingerprint/DeviceTemplateBuilder.cs (Build(), lines 164-182); F:/projects/ghost_shell_desktop/src/GhostShell.Runtime/Fingerprint/CoherenceValidator.cs:266-274; F:/projects/chromium/src/third_party/blink/renderer/platform/ghost_shell_config.cc:452-469`
- **Detail:** DeviceTemplateBuilder.Build() emits version, profile_name, template_name, hardware, languages, screen, graphics, gpu, audio, timezone, battery, connection, media, noise, fonts, ua_metadata, codecs, plugins, permissions — and NO "tls" key. CoherenceValidator self-documents this: the ja3 check is hard-coded Skip with detail 'field not present in fingerprint — runtime check needed' (line 271). The C bridge parser EnsureBridgeInitialized() only fills tls_cipher_suites / tls_supported_groups from dict.FindDict("tls") (config.cc line 452); when the key is absent both vectors stay empty, so GhostShell_GetTLSCipherSuites/SupportedGroups return 0 for every profile.
- **Impact:** Every Ghost Shell profile presents the byte-identical Chrome-default cipher list and supported_groups to the server. JA3 cipher field and JA3 supported_groups field are constant across the entire pool; JA4's cipher hash (a_ component) and supported-group component are constant. A DataDome/Cloudflare/Akamai JA3/JA4 cluster sees one fingerprint shared by thousands of 'distinct' profiles — a textbook proxy/anti-detect pool signal. The advertised 'per-profile JA3' feature is non-functional.
- **Fix:** Add a BuildTls() emitter to DeviceTemplateBuilder and wire it into Build() as ["tls"] = BuildTls(). Emit {"cipher_suites":[...uint16...],"supported_groups":[...uint16...]} derived deterministically from a Chrome-realistic template set (e.g. pick one of a handful of real captured Chrome 149 cipher orderings keyed by profile hash) rather than a free random shuffle. Then re-enable the CoherenceValidator JA3 check to assert the key exists and the lists are non-empty and Chrome-plausible. Add an integration test that base64-decodes the emitted payload and asserts dict["tls"]["cipher_suites"].Count > 0.

### `TLS-02` — TLS 1.3 cipher suites are hardcoded — override cannot change the suites JA4 fingerprints on a 1.3 handshake  *(high · coverage-gap)*

- **File:** `F:/projects/chromium/src/third_party/boringssl/src/ssl/handshake_client.cc:111-145 (ssl_write_client_cipher_list); F:/projects/chromium/src/net/socket/ssl_client_socket_impl.cc:793-817`
- **Detail:** The GhostShell cipher override re-runs SSL_set_strict_cipher_list with a profile-specific name list. But ssl_write_client_cipher_list emits TLS 1.3 ciphers from fixed C arrays kCiphersAESHardware/kCiphersNoAESHardware/kCiphersCNSA (lines 114-128) chosen only by EVP_has_aes_hardware()/compliance policy — these come BEFORE the TLS 1.2 ciphers in the ClientHello and are entirely independent of the strict cipher list. Only the TLS 1.2 suites (loop over SSL_get_ciphers at line 149) honor the GhostShell ordering. On a modern TLS 1.3 negotiation, JA4 records the offered suites; the 1.3 suites (1301/1302/1303) plus their AES-vs-ChaCha ordering are therefore fixed by host AES-NI, not by the profile.
- **Impact:** Two profiles on the same hardware produce the same leading 1.3 cipher triple and the same AES/ChaCha ordering regardless of any cipher_suites override. JA4's cipher component (sorted, but still a fixed multiset+ordering signal in JA4_o/raw) does not vary per profile from this vector. The override gives a false sense of cipher diversity.
- **Fix:** Either (a) accept that 1.3 cipher order is hardware-bound (it genuinely is in real Chrome — this is actually correct stealth, so document it and ensure the spoofed aes_hw_override matches the claimed CPU), or (b) if true per-profile 1.3 cipher ordering is desired, patch ssl_write_client_cipher_list to consult the GhostShell bridge for the 1.3 suite order too, guarded so it only ever produces orderings real Chrome emits (AES-first or ChaCha-first). Prefer (a): drive has_aes_hw from a config flag tied to the spoofed CPU so the 1.3 cipher order is coherent with the advertised hardware rather than the real host.

### `TLS-03` — signature_algorithms are constant across all profiles and not part of the override  *(high · missing-vector)*

- **File:** `F:/projects/chromium/src/net/socket/ssl_client_socket_impl.cc:847-856 (kVerifyPrefs); F:/projects/chromium/src/third_party/boringssl/src/ssl/extensions.cc:290-338 (kVerifySignatureAlgorithms)`

The signature_algorithms list is a first-class JA4 component (JA4 hashes the sorted sigalg list as part of the _c segment) and is also visible in JA3 fullstring extension data.
- **Impact:** JA4's signature-algorithm hash is identical for every Ghost Shell profile. Combined with TLS-01/TLS-02, the only thing JA4 sees varying across profiles is nothing — JA4 collapses the whole pool to one fingerprint. Anti-bot vendors increasingly prefer JA4 precisely because it is robust to the extension-shuffle that Ghost Shell relies on.
- **Fix:** Add a tls.signature_algorithms list to the payload + a GhostShell_GetTLSSigAlgs bridge, and apply it via SSL_set_verify_algorithm_prefs in Init() when the profile provides one (validated against a small set of real Chrome 149 sigalg orderings). ### `TLS-07` — JA4/JA4_r resilience: per-profile uniqueness rests solely on extension order, which JA4 sorts away  *(high · currency)*

The self-check has been tuned to ignore the very leak the patch introduces.
- **Impact:** Internal QA reports WebRTC as 'safe' while external anti-bot systems see the non-Chrome raw-private-IP-without-mDNS pattern and flag it. False confidence that the WebRTC zone is healthy.
- **Fix:** After adopting the mDNS-on fix (WRTC-02), tighten IsTrivialIp so that on a build that is SUPPOSED to use mDNS, ANY raw private IPv4 host candidate (not a .local name) is treated as a FAIL, not trivial. Add a distinct check 'webrtc.mdns_present' that fails if any host candidate is a literal IP rather than a *.local hostname, so QA catches the regression that external detectors catch.

### `H2-02` — No HTTP/2 fingerprint configuration surface in GhostShellConfig — entire H2 vector is unwired to the payload  *(low · missing-vector)*

- **File:** `F:/projects/chromium/src/third_party/blink/renderer/platform/ghost_shell_config.h:16-220 ; F:/projects/chromium/src/third_party/blink/renderer/platform/ghost_shell_config.cc:84-330`
- **Detail:** GhostShellConfig exposes no GetHttp2* getters, and the bridge (ghost_shell_config.cc:475-514) exposes only IsActive/RandomSeed/TLSCipherSuites/TLSSupportedGroups. The payload (parsed in Initialize, lines 111-330) has hardware/languages/screen/graphics/gpu/audio/timezone/battery/connection/media/noise/fonts/ua_metadata/codecs/plugins/permissions/tls — but NO 'http2' key and NO 'webrtc' key. So the H2 and WebRTC zones consume only the global random seed. The Akamai H2 fingerprint and any per-profile WebRTC behavior cannot be differentiated beyond the seed-derived (and currently dead) grease.
- **Impact:** Per-profile H2 fingerprints are impossible; every Ghost Shell profile presents the identical stock-Chrome H2 fingerprint. That is internally coherent but means H2 is a profile-linkability surface if combined with other near-stock vectors: a pool of profiles all sharing one exact H2 hash is fine (it matches real Chrome) but offers no entropy. The bigger issue is the WebRTC side has no config to make the fake-IP coherent with the profile's claimed geo/ISP.
- **Fix:** Add an optional 'http2' payload section + getters (settings values, window-update increment, header-priority/order toggle) and a 'webrtc' section (ip_handling_policy string, fake-LAN strategy, whether to keep mDNS). Wire the WebRTC policy getter into the experimental-prefs writer (WRTC-01) and the fake-LAN getter into the C-bridge so peer_connection.cc/socket_manager.cc can consume real config instead of just the seed.

**New-patch ideas (HTTP/2 & WebRTC):**

- **Set webrtc.ip_handling_policy preference (the real Chrome-149 control) and stop relying on the dead switch** [WebRTC IP handling] — WRTC-01 shows --force-webrtc-ip-handling-policy is ignored in 149. The only honored path is prefs::kWebRTCIPHandlingPolicy. Writing the pref into Default/Preferences makes the policy actually engage, which in turn flips enable_default_local_candidate handling and the SanitizeCandidate raddr-clearing branches. _(In ChromeOptionsBuilder.cs experimental-prefs block (~line 304), add options.AddUserProfilePreference("webrtc.ip_handling_policy", "default_public_interface_only") for the no-proxy case and "disable_non_proxied_udp" for the proxied case. Cross-check the exact pref key name against components/embedder_support or prefs registration in 149. Add a renderer-side VLOG assert that the resolved policy != kDefault.)_
- **Keep native mDNS ON and delete GhostShellFakeLanIP; let Chrome's .local obfuscation do the work** [WebRTC host candidate privacy] — The single most undetectable WebRTC posture is to behave exactly like stock Chrome 149: mDNS .local host candidates, raddr cleared on srflx. The current patch fights this and produces a non-Chrome raw-IP pattern. Removing the fake-IP rewrite and the WebRtcHideLocalIpsWithMdns disable instantly eliminates WRTC-02/04/05/07. _(Remove 'WebRtcHideLocalIpsWithMdns' from ChromeOptionsBuilder.cs:291. Delete the GhostShellFakeLanIP namespace and its call site at peer_connection.cc:2657-2659. Re-run a STUN probe to confirm candidates are <uuid>.local with empty raddr.)_
- **Scrub the network-service default local address under the GhostShell filter** [WebRTC default local candidate] — WRTC-03: the 8.8.8.8-connect default-local-address path is the one place the host-scope filter does not cover, and it delegates through EmptyNetworkManager. Scrubbing it closes the default-route leak independently of the policy fix. _(In socket_manager.cc MaybeFinishDoGetDefaultLocalAddresses (or SendNetworkList), when GhostShellShouldFilterHostCandidates() is true, overwrite both default addresses with net::IPAddress() before NetworkListChanged. Add a unit test in socket_manager_unittest.cc asserting the default addresses are empty when the bridge is active.)_
- **If a fake LAN IP is mandatory, make it config-driven, coherent, and varied** [WebRTC fake host IP realism] — Some sites reject .local candidates. If a fake IP must be emitted, a static 192.168.x.x derived from one seed is the worst option (WRTC-02). It should vary per interface, span realistic ranges, and be IPv6-aware. _(Add a 'webrtc' payload section + C-bridge getters (e.g. GhostShell_GetFakeLanIPv4/IPv6 returning per-profile values across 10/172.16/192.168 with a randomized 3rd octet, and a fd00::/8 v6). Make GhostShellFakeLanIP family-aware and consume these instead of recomputing from the raw seed. Recompute candidate foundation after rewrite (WRTC-05).)_
- **Add a curated, real-Chrome H2 SETTINGS profile selector (no GREASE)** [HTTP/2 Akamai fingerprint] — H2-01/H2-02: the current H2 customization is dead grease. Real per-profile H2 entropy should come from selecting among genuine Chrome-build SETTINGS/window values, never from adding a grease entry no real Chrome sends. _(Add payload 'http2': {header_table_size, initial_window_size, max_header_list_size, max_concurrent_streams_omit, session_recv_window} validated against a table of real Chrome 149.x values. Consume in net/http/http_network_session.cc AddDefaultHttp2Settings via GhostShellConfig getters (network-process-safe C-bridge). Keep enable_http2_settings_grease=false always.)_

**Engine-feature ideas:**

- **Compile-time-removable, single-source GhostShell WebRTC policy resolver baked into the renderer prefs path** — WRTC-01 happened because the stealth control (a CLI switch) and the engine's actual mechanism (a pref) drifted apart across Chrome versions. Building the WebRTC IP-handling decision directly into renderer_preferences_util.cc / peer_connection_dependency_factory.cc — reading GhostShellConfig once and setting webrtc_ip_handling_policy + allow_mdns_obfuscation + enable_default_local_candidate atomically — removes the fragile launcher-switch dependency and guarantees the policy can never silently fall back to kDefault on a version bump.
- **Pre-build 'real-Chrome candidate parity' self-test harness wired into the build** — WRTC-06 shows internal QA can be tuned to hide the leak it should catch. A build-time harness that launches the engine against a local STUN server and asserts candidate shape matches a captured stock-Chrome-149 baseline (host = *.local, srflx raddr empty, no raw RFC1918, no global IPv6) would catch WRTC-02/04/07 regressions before shipping, independent of the application self-check.
- **Network-service-level egress IP coherence guard** — WRTC-03 plus the proxy architecture means the default local address and any leaked candidate must be consistent with the proxy egress. A small engine feature that, when the GhostShell bridge is active and a proxy is configured, hard-zeroes all non-proxied default/local addresses at the P2PSocketManager boundary (a single chokepoint) would make real-IP egress through WebRTC structurally impossible rather than relying on multiple per-candidate patches.
- **Bake the H2/TLS fingerprint into a versioned 'browser identity' table validated against live Chrome captures** — H2-01/H2-02: rather than ad-hoc patches, ship a curated table mapping each spoofed Chrome version to its exact real SETTINGS/window/priority + JA3/JA4 + UA metadata, validated in CI against captures from real Chrome of that version. The engine selects one coherent row per profile, so the H2 hash, TLS hash, and UA can never disagree — eliminating the cross-vector incoherence that detectors like Akamai/Cloudflare key on.

### Deliberate decisions (NOT bugs)
- **TLS per-profile cipher/group lists — intentionally NOT emitted.** Real Chrome
  installs share one cipher list; per-connection JA3 variation comes from GREASE +
  extension permutation, not per-profile lists. Emitting per-profile lists would
  make GhostShell profiles *less* like real Chrome. The bridge is complete and
  inert (returns stock), so JA3/JA4 **matches** real Chrome 149. (PCP-01/H2-01)
- **WebRTC fake-IP strategy kept over native-mDNS swap (WRTC-02).** The mDNS-native
  posture (`.local` host candidates) is the most undetectable long-term, but the
  swap conflicts with the current fake-IP rewrite and needs live STUN QA. Current
  fake-IP approach functionally prevents the leak today.
- **HTTP/2 = stock Chrome (no GREASE).** H2 grease path left disabled; stock H2
  fingerprint already matches real Chrome and is the safest. (H2-01/H2-02)
