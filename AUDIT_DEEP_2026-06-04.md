# GhostShell — Deep Logic Audit (2026-06-04)

10-zone parallel audit + adversarial verification. 80 findings total — critical=12, high=21, medium=25, low=22. Verdicts: confirmed=27, rejected=5, uncertain=1, unverified(med/low)=47.


## Fingerprint coherence & device templates

> This zone has severe, systemic fingerprint-incoherence defects that directly undermine the product's entire value proposition. The DeviceTemplateBuilder only knows two OS shapes (Windows desktop and Android mobile): every Apple/Mac template, every tablet, and every iPhone is rendered as a Frankenstein fingerprint (e.g. iPhone -> Android UA + Linux platform + "Apple Apple GPU" + Windows fonts), and four Mali-GPU Android phones fall through to an Intel Direct3D11 WebGL renderer. The CoherenceValidator that is supposed to catch exactly these mismatches is largely cosmetic — several of its "critical" checks (GPU-vs-OS, navigator.vendor, webdriver) are hardcoded to Pass and the rest are too shallow to catch any of the real incoherences, so these broken profiles score 100/EXCELLENT. Additionally the timezone is hardcoded to Europe/Kyiv on both the scoring and the real launch path regardless of proxy geo (a textbook timezone-vs-IP leak), GPU PCI device IDs are constants that contradict the renderer string, and network/audio values are off the privacy-rounding grid real Chrome uses. The non-anti-detect correctness of the persistence/monitor code is mostly sound.

### `FINGERPRINT-01` — Apple/Mac and tablet desktop templates emit a Windows user agent + Win32/Linux platform while exposing Apple GPU strings — irreconcilable OS incoherence  *(critical, confirmed)*

- **File:** `src/GhostShell.Runtime/Fingerprint/DeviceTemplateBuilder.cs:177-199, 319-338, 529-578`  ·  **Category:** detection-leak
- **Problem:** BuildUserAgent() only branches on FormFactor.Mobile vs everything-else: FormFactor.Desktop and FormFactor.Tablet both return the hardcoded Windows UA 'Mozilla/5.0 (Windows NT 10.0; Win64; x64)...'. TemplatePlatform() returns 'Win32' for Desktop and 'Linux armv8l' for Tablet, and ua_metadata.platform returns 'Windows' for everything non-mobile. But the catalog ships Apple desktops (macbook_pro_16_m3_max, mac_studio_m2_ultra — FormFactor.Desktop, Apple GPU) and a tablet (ipad_air_m2 — FormFactor.Tablet, Apple GPU). For the MacBook this produces: navigator.userAgent='...Windows NT 10.0...', navigator.platform='Win32', Sec-CH-UA-Platform='Windows', architecture='x86' — yet ResolveGpuStrings() returns WebGL UNMASKED_VENDOR='Apple Inc.' and renderer='Apple Apple M3 Max'. - **Impact:** Any anti-bot stack that cross-references navigator.userAgent / navigator.platform / Sec-CH-UA-Platform against the WebGL unmasked vendor (a standard, cheap check) instantly sees an impossible device — a Windows machine reporting an Apple GPU, or a UA/platform/uaCH disagreeing on the OS. ### `FINGERPRINT-08` — Mobile/tablet screen reports a fabricated desktop taskbar (availHeight gap) and nonzero screen offset  *(medium, unverified)*

### `FINGERPRINT-09` — navigator.connection rtt/downlink not on Chrome's privacy-rounding grid  *(medium, unverified)*

- **File:** `src/GhostShell.Runtime/Fingerprint/DeviceTemplateBuilder.cs:451-458`  ·  **Category:** detection-leak
- **Problem:** BuildConnection() sets rtt = _rng.Next(40,100) (arbitrary integers like 47, 83) and downlink = Math.Round(8 + rng.NextDouble()*4, 1). Real Chrome deliberately rounds NetworkInformation.rtt to the nearest 25 ms (0, 25, 50, 75, 100, ...) and downlink to the nearest 0.025 Mbps (then caps ~10) for privacy. Values not on these grids cannot be produced by a genuine Chrome.
- **Impact:** A detector that knows Chrome's rounding rule sees rtt=47 / downlink=10.3 as impossible and flags the NetworkInformation values as synthetic. Lower-severity than the OS issues but still a deterministic tell present on every profile.
- **Proposed fix:** Quantize rtt to multiples of 25 (e.g. pick from {0,25,50,75,100}) and downlink to multiples of 0.025 within Chrome's observed cap. Keep the per-profile RNG for selection so the value stays stable.

### `SELFCHECK-01` — WebRTC leak detection ignores IPv6 candidates — real IPv6 interface address leaks pass as "safe"  *(medium, confirmed)*

- **File:** `src/GhostShell.Runtime/Browser/SelfCheckService.cs:324-365`  ·  **Category:** detection-leak
- **Problem:** The WebRTC probe extracts candidate IPs with an IPv4-only regex (line 336: the '\b(?:25[0-5]|...)\.{3}...' dotted-quad pattern). ICE host/srflx candidates for IPv6 (e.g. '2001:...', or temporary IPv6 privacy addresses, or a real global IPv6 from the host NIC when the proxy is IPv4-only) are never matched, so they are never added to the 'ips' set and never evaluated by IsTrivialIp. The C# side then sees an empty array and sets webrtcLeak=false. IsTrivialIp (lines 878-893) is also IPv4-only and has no '::1'/'fe80:'/'fc00::/7' handling. On any dual-stack host, Chrome routinely surfaces a global IPv6 candidate that bypasses an IPv4 proxy entirely, revealing the user's real ISP/location.
- **Impact:** A profile that is leaking its real IPv6 address via WebRTC will be reported by the self-check as 'WebRTC Leak: (safe)' with status=pass. The operator believes the profile is leak-free and uses it; anti-bot stacks that read RTCPeerConnection candidates see the real IPv6 and deanonymize/flag the profile. This is a silent identity leak — the worst possible outcome for an antidetect product.
- **Proposed fix:** Add an IPv6 candidate regex (or just split on the candidate SDP fields and parse the connection-address token) so IPv6 candidates are extracted. Extend IsTrivialIp to treat ::1, fe80::/10 (link-local), fc00::/7 (ULA), and mDNS '.local' hostnames as trivial, and treat any other global IPv6 as a leak. Better: in the JS probe, resolve any '*.local' mDNS candidate and flag non-loopback non-ULA addresses of either family.
- **Verifier (confirmed):** The cited code is real and accurately located. SelfCheckService.cs line 336 extracts WebRTC candidate IPs with a strictly IPv4 dotted-quad regex (`\b(?:(?:25[0-5]|2[0-4][0-9]|[01]?[0-9][0-9]?)\.){3}(?:25[0-5]|...)\b`). IPv6 ICE candidates (2001:..., fe80::..., or mDNS *.local) produce no match, so they are never added to the `ips` Set returned to C# (lines 330-338). On the C# side (lines 349-359) an empty/IPv6-only candidate array leaves `webrtcLeak=false`, and the result (lines 818-821) is then reported as Status="pass", Actual="(safe)", Severity="critical". IsTrivialIp (lines 878-893) is also IPv4-only with no ::1 / fe80::/10 / fc00::/7 handling — though that branch is moot since IPv6 candidates never reach it (the JS regex filters them out first). So the self-check probe is genuinely blind to IPv6 WebRTC candidates and would report "safe" for an IPv6-only leak. The technical description of the defect and its location are correct.

However, the CLAIMED IMPACT is overstated. The actual WebRTC leak PREVENTION is not this probe but the launch-time flag `--force-webrtc-ip-handling-policy=disable_non_proxied_udp` (ChromeOptionsBuilder.cs line 194, with an explanatory comment at 191-193), which suppresses non-proxied UDP host candidates of BOTH IP families at the source. The genuine problem is a defense-in-depth gap: if the primary mitigation ever regresses or is misconfigured, the self-check would falsely report an IPv6 leak as "safe" (false assurance). That is real and worth fixing, but it is a verification-layer coverage gap one step behind the actual control, not a guaranteed live identity leak. Hence confirmed but downgraded from critical to medium.

## ScriptRunner automation engine

> ScriptRunner.cs is large but generally careful about control flow, sandboxing (CSV/screenshot path containment), SSRF, secret redaction, and own-domain fraud-click guards. However it has one foundational and severe anti-detection defect: every browser interaction (click, type, hover, press_key, scroll, ad-click) is driven exclusively through JS-dispatched synthetic events (isTrusted=false, no real key events, geometric-center clicks), which modern anti-bot stacks trivially flag — this undermines the product's entire "undetectable" value proposition. There are also two real correctness regressions in the graph-mode executor: the sub-graph loop-body executor swallows cancellation and dead-session/abort signals (the browser keeps automating after Stop or after the session dies), and ExecuteAsync discards the typed CaptchaRecoveryAbortException so post-captcha proxy rotation / auto-relaunch never fires. Plus several lower-severity behavioral tells (no-op rotate_ip reported as success, fixed-delay waits, missing typing key events).

### `SCRIPTRUNNER-01` — All clicks/typing/key/hover events are synthetic JS events (isTrusted=false) — trivially bot-detectable  *(critical, confirmed)*

- **File:** `src/GhostShell.Runtime/Scripts/ScriptRunner.cs:1633-1704, 1736-1743`  ·  **Category:** detection-leak
- **Problem:** Every interaction handler dispatches DOM events from JavaScript via ExecuteScriptAsync rather than through the OS or CDP Input domain. click/click_selector and double_click call Humanizer.ClickAsync which does el.dispatchEvent(new MouseEvent('mousedown'/'mouseup'/'click', ...)); right_click dispatches new MouseEvent('contextmenu'); hover dispatches new MouseEvent('mouseover'); press_key dispatches a single new KeyboardEvent('keydown') (no keypress/keyup/beforeinput/input); type routes to Humanizer.TypeAsync which sets el.value += c and fires only an InputEvent('input'). IBrowserSession (IBrowserLauncher.cs) exposes only ExecuteScriptAsync/NavigateAsync — there is NO native or CDP Input.dispatchMouseEvent/dispatchKeyEvent path. JS-constructed events always carry event.isTrusted === false, and real typing always emits keydown/keypress/keyup with matching key codes plus selectionchange. move_random is a pure idle pause with no cursor movement at all.
- **Impact:** isTrusted===false on every click and the absence of keydown/keyup during typing are first-line, well-known anti-bot signals (used by reCAPTCHA, Cloudflare Turnstile, DataDome, PerimeterX). Any site listening for trusted events or correlating key/mouse event streams will classify the profile as automated regardless of how good the fingerprint spoofing is. This defeats the product's core 'undetectable as automated' guarantee for every profile that runs a script that clicks or types.
- **Proposed fix:** Route real input through CDP Input.dispatchMouseEvent / Input.dispatchKeyEvent (or OS-level SendInput, which the Humanizer header already anticipates as the planned integration point) so events are browser-generated and isTrusted===true. ## Proxy & network leaks

> The proxy stack is mostly solid on the highest-stakes leak vectors: the forwarder binds to IPv4 loopback only, credentials are kept off the Chromium command line and out of logs, and ChromeOptionsBuilder forces --no-proxy-server / WebRTC suppression to avoid system-proxy and STUN leaks. However there are real defects: the auth forwarder only injects Proxy-Authorization into the FIRST request on a keep-alive HTTP connection (subsequent requests on the same socket go upstream un-authenticated and are rejected with 407), IPv6 proxies are mis-serialized by ProxyParser into a malformed URL that breaks every downstream consumer (and the forwarder binds IPv4-only loopback so it can't be reached if Chromium prefers ::1), the HttpProxyTester reports a working proxy whose scheme silently differs from the stored URL without persisting the corrected scheme (Chromium then uses the wrong/declared scheme → connection failure or, for a misdeclared SOCKS-as-HTTP proxy, a DNS-resolved-locally leak), and several counter/robustness issues. None are catastrophic real-IP leaks at the browser layer, but the SOCKS-scheme mismatch and the credential-stripped fallback are genuine correctness/leak-adjacent risks.

### `PROXY-02` — IPv6 proxies are serialized into a malformed URL (host not bracketed), breaking every downstream Uri-based consumer  *(high, confirmed)*

- **File:** `src/GhostShell.Core/Models/ProxyParser.cs:110-118, 212-218`  ·  **Category:** correctness
- **Problem:** The IPv6 branch parses '[2001:db8::1]:1080' into host='2001:db8::1' (unbracketed) and passes it to Ok(), which builds the canonical URL as `$"{scheme}://{creds}{host}:{port}"` = 'http://2001:db8::1:1080'. That string is not a valid URI — the colons in the address are indistinguishable from the port delimiter. This URL becomes the proxy's stored Url (source of truth). Downstream, ProxyUrl.TryParse, HttpProxyTester.TryParseProxyUrl, and HttpConnectForwarder.StartAsync all do Uri.TryCreate on it and then read uri.Host / uri.Port, which will mis-split host/port (Uri treats the last colon group as authority and parsing of the port is wrong/garbage).
- **Impact:** Any IPv6 proxy the user imports (a normal case for residential/mobile IPv6 pools in anti-detect work) is stored in a corrupt form. The proxy test will probe the wrong host:port (false negative, or worse a false positive against an unintended endpoint), and at launch the forwarder/Chromium get a bad host:port. Either the profile fails to launch or it connects somewhere unintended — both defeat the leak-free guarantee.
- **Proposed fix:** In ProxyParser.Ok() (and anywhere a host is interpolated into a URL), bracket IPv6 literals: `var hostPart = host.Contains(':') && !host.StartsWith("[") ? $"[{host}]" : host;` then build `$"{scheme}://{creds}{hostPart}:{port}"`. Apply the same bracketing in HttpProxyTester's proxyUri construction (`$"{scheme}://{host}:{port}"`) and verify ProxyUrl.HostPort renders bracketed too.
- **Verifier (confirmed):** The defect is real and the cited locations are accurate. In ProxyParser.cs the IPv6 regex (line 33: `^\[([0-9a-fA-F:]+)\]:([0-9]{1,5})...`) captures the address WITHOUT brackets; line 114 reads `host = m.Groups[1].Value` (e.g. "2001:db8::1") and line 118 passes that unbracketed host to Ok(). Ok() (line 218) builds `url = $"{scheme}://{creds}{host}:{port}"` with no re-bracketing, yielding the malformed `http://2001:db8::1:1080`. That string is stored as the source of truth: ProxyViewModel.BulkImportAsync (line 165) copies ParsedProxy.Url straight into Proxy.Url, which is persisted by ProxyService and later consumed by HttpProxyTester.TryParseProxyUrl (Uri.TryCreate), HttpConnectForwarder.StartAsync (Uri.TryCreate, line 90), and BrowserLauncher (proxy.Url passed to forwarder/Chromium, line 107). All consumers and the data flow in the finding are confirmed.

I empirically tested the actual .NET 8 Uri behavior, which REFINES one claim in the finding: `Uri.TryCreate("http://2001:db8::1:1080", Absolute, out _)` returns FALSE, not a mis-split host/port. So the auditor's specific assertion that Uri "treats the last colon group as authority and parsing of the port is wrong/garbage," producing a false positive "against an unintended endpoint," is INCORRECT — the URL is rejected outright. The real consequence is fail-closed: HttpProxyTester returns Ok=false with "URL malformed: could not parse URI", and HttpConnectForwarder.StartAsync throws ArgumentException, so the profile fails to launch. (For a credential-less IPv6 proxy the raw malformed string would be handed to Chromium's --proxy-server, which likewise cannot parse it.) There is no silent leak to an unintended endpoint.

Net: every IPv6 proxy parsed through the dedicated IPv6 branch is stored in a corrupt, unusable form — it always fails its test and always fails to launch. The proposed fix (bracket IPv6 literals in Ok() and in HttpProxyTester's proxyUri construction) is correct. The defect is genuine; only the leak/false-positive mechanism in the impact narrative is overstated.

### `PROXY-01` — Auth forwarder injects Proxy-Authorization only on the first request of a keep-alive HTTP connection  *(medium, confirmed)*

- **File:** `src/GhostShell.Runtime/Proxy/HttpConnectForwarder.cs:184-227`  ·  **Category:** correctness
- **Problem:** HandleConnectionAsync reads exactly ONE header block via ReadHeadersAsync, calls InjectAuth on it, writes it upstream, then switches to a raw byte pump (CountingCopyAsync) for the remainder of the connection. For HTTPS this is correct (only the single CONNECT needs auth). But for a plain-HTTP upstream proxy serving HTTP origins, Chromium reuses one TCP connection for many pipelined/keep-alive requests (GET http://a/, GET http://b/, ...). Only the first GET gets Proxy-Authorization injected; every subsequent request on that socket is forwarded verbatim with no auth header, so the upstream proxy answers 407 Proxy Authentication Required for all of them.
- **Impact:** Profiles assigned an authenticated HTTP proxy (the exact case this forwarder exists for) will load the first HTTP resource then fail every subsequent same-connection HTTP request with 407. Pages partially load or break, which is both a functional outage and a detectability signal (broken resource loading patterns differ from a real user). HTTPS sites mask the bug because each CONNECT tunnel is a fresh first-request, which is why it can ship unnoticed yet still break plain-HTTP browsing/ad-verification flows.
- **Proposed fix:** Detect non-CONNECT (plain HTTP) requests and re-parse/inject auth per request rather than pumping raw after the first header block: for the client→upstream direction, keep framing HTTP requests and call InjectAuth on each request-line+headers block until the connection upgrades or closes. For CONNECT keep the current raw-tunnel behaviour after the 200 response. At minimum, document that only HTTP CONNECT (HTTPS) upstream usage is supported and reject/flag plain-HTTP-proxy use.
- **Verifier (confirmed):** The defect is real and the cited location (HttpConnectForwarder.cs:184-227) is accurate. HandleConnectionAsync reads exactly one header block via ReadHeadersAsync (line 184), calls InjectAuth once (line 200), writes it upstream (line 201), then switches to a raw byte pump (CountingCopyAsync, lines 225-227) for the rest of the connection. Neither CountingCopyAsync (lines 259-275) nor any other code re-frames or re-injects auth on subsequent requests. The class doc itself (lines 25-27) states it injects auth into "the FIRST request line we read off the wire." I verified the deployment path: BrowserLauncher.NeedsAuthForwarder (lines 502-516) starts this forwarder precisely for HTTP/HTTPS upstream proxies carrying embedded user:pass@ credentials — exactly the authenticated-HTTP-proxy case the finding targets — and ChromeOptionsBuilder (line 131) hands Chromium --proxy-server=http://127.0.0.1:PORT pointing at the forwarder. The load-bearing premise holds: for plain-HTTP origins Chromium sends absolute-form requests (GET http://host/path) to the proxy and reuses one keep-alive TCP connection for many requests; only request #1 on that connection gets Proxy-Authorization injected, so the authenticated upstream returns 407 for requests 2..N. HTTPS is correctly handled because each CONNECT is a fresh first-request and the tunnel is opaque afterward, which is exactly why the bug ships unnoticed. No mitigation exists elsewhere in the code path. The control flow is not misread and no upstream validation prevents this. I downgrade from high to medium: the first HTTP request on each connection always succeeds (partial-load, not total outage), the symptom is intermittent and HTTPS is unaffected, and plain-HTTP origins are a shrinking fraction of real traffic — but it remains a genuine correctness defect in the exact use case this component exists to serve.

### `PROXY-03` — Forwarder binds IPv4 loopback only; IPv6 upstream connect uses unbracketed/bracketed host inconsistently  *(medium, unverified)*

### `PROXY-09` — ProxyParser 4-part tie-break can route to user_pass_host_port when both sides have valid ports, mis-assigning host/creds  *(medium, unverified)*

> This zone contains one catastrophic security hole and several real correctness/integrity bugs. ### `DATA-01` — Self-update downloads and executes a ZIP with no checksum/signature/Authenticode verification (RCE via update channel)  *(critical, confirmed)*

- **File:** `src/GhostShell.Data/Services/GitHubUpdateService.cs:376-757`  ·  **Category:** security
- **Problem:** ApplyAsync downloads info.PortableZipUrl (line 456), streams it to disk (lines 474-499), extracts it (lines 520-552), validates only that GhostShell.exe exists and is non-empty (lines 564-570), then writes a PowerShell helper that copies every extracted file over the live install directory and relaunches GhostShell.exe (lines 676-705). At no point is the downloaded artifact's integrity or authenticity verified: there is no SHA-256/SHA-512 comparison against a published digest, no detached-signature check, no GPG/PGP check, and no Authenticode signature validation of the extracted .exe. A grep of the file confirms no hash/checksum/signature/verify logic exists anywhere. PortableZipUrl is taken verbatim from the GitHub release JSON's browser_download_url (lines 328-330, 345). Anyone who can serve/influence that release JSON or the asset bytes — a compromised/hijacked GitHub repo or release, a stolen maintainer token, a release asset re-upload, or a man-in-the-middle on the asset CDN — gets arbitrary native code copied over the install and executed on the next launch.
- **Impact:** Full remote code execution on every user who clicks 'update'. For an antidetect product this is maximal severity: an attacker can ship a build that silently exfiltrates the encrypted vault, real IP, all profile fingerprints/proxies, or that disables stealth so every profile becomes detectable. The update channel is the single most trusted code path in the app and it is completely unauthenticated.

### `DATA-05` — Daily-fire cap is enforced by a non-atomic read-then-act + read-reset, letting a schedule exceed its runs_per_day quota  *(medium, unverified)*

### `DATA-04` — Tolerant migrations (V11, V13–V28, incl. V23 DROP+CREATE) run without a transaction — partial application corrupts the schema  *(low, confirmed)*
